## What was built

### Database: `supabase/migrations/20261024090000_analytics.sql`

The file sorts after main's newest migration (`20261023090000_security_digest.sql`). It is read-only: no tables, no
views, no triggers.

| Object | Kind | What it does |
|---|---|---|
| `public.analytics_activity(p_from, p_to, p_user)` | block | Calls, reached calls, emails, WhatsApp messages and meetings per day or ISO week. Totals include meetings held. The team view adds `by_person`, where `user_id` null means former team members |
| `public.analytics_pipeline(...)` | block | Opened, won, lost (Opened by mistake counted apart), win rate (from 5 closed deals), cycle (median and mean from 3 won deals), funnel from non-undone stage history, days in stage, lost reasons, and per owner for the team |
| `public.analytics_speed(...)` | block | Leads added by hand in the range. Time to first touch (call, email, WhatsApp or meeting, by anyone) in five buckets |
| `public.analytics_call_times(...)` | block | Weekday × hour of calls (Paris time), with calls and reached per cell, and `min_calls` 5 |
| `public.analytics_sales(...)` | block | Revenue and sales of confirmed sales per bucket, totals with the split by fulfilment, and the top 10 products by `lower(product_name)` with the newest spelling |
| `public.analytics_coverage(p_user, p_idle_days)` | block | Right now: untouched leads (exactly `lead_filter_sql`'s inactive rule), never contacted, no next step, overdue tasks |
| `public.analytics_batches(p_user, p_limit)` | block | Admins only: list quality per imported lead batch, counting only entries and deals made after the import |
| `private.analytics_owner(p_user)` | helper | Who the figures are for. aal2 required (42501 `forbidden`). A rep always gets their own figures (42501 `scope` when asking for someone else). A manager or admin gets the team (null) or one member of the organisation; anyone else gets P0002 `rep` |
| `private.analytics_window(p_from, p_to)` | helper | The Paris instants `[from 00:00, to+1 00:00)` and the bucket size. 1 to 366 days, never after Paris today, else 22023 `bounds` |
| `private.analytics_buckets(...)` | helper (added) | Every bucket including empty ones, with `partial` on weeks |
| `private.analytics_activity_rows` / `_deal_rows` / `_lead_rows` / `_sale_lines` | source helpers (added) | Team and person as separate static statements, each with a fixed index condition. Each block reads its source rows once |
| `activities_no_author_idx` | index | `(org_id, created_at) where user_id is null`: former members' entries without a full scan |

Every function:
- is SECURITY INVOKER, `stable`, with `set search_path = ''`;
- runs static SQL only (Gate 1 G6: no dynamic statements or string building);
- has `revoke all from public, anon` and `grant execute to authenticated`;
- never reads an entry's body, a lost note, a cancel reason, a sale's note or a cost.

The seven blocks and the four source helpers also carry `plan_cache_mode = force_custom_plan` and `jit = off`.

The new functions need no change to `gate1_attack.sql`:
- G4 lists SECURITY DEFINER functions only, and these are all INVOKER.
- G5 (no PUBLIC execute) and G6 (dynamic SQL) pick them up automatically.
- Both pass, as `db-test.sh` shows.

### Server data layer: `src/lib/analytics/`

| File | Server-only | What |
|---|---|---|
| `params.ts` | no (pure) | Range presets, custom dates (366-day and 54-week cap), person and idle filters. The strict API parse refuses unknown and repeated keys; the lenient page parse drops bad values. `resolveRange(params, parisToday)` in Paris time, plus `parisToday`, `bucketCount` and the shared literals |
| `parts.ts` | no (pure) | A `strictObject` result schema per block, at every level, with bounds: non-negative integer counts, money as `^\d{1,16}(\.\d{1,2})?$`, buckets ≤ 31 days or ≤ 54 weeks, cells ≤ 168, products ≤ 10, batches ≤ 50, reasons ≤ 8, stage and reason enums |
| `fetch.ts` | no (pure) | `runAnalytics(rpc, query, role)`, described below |
| `server.ts` | **yes** (`import "server-only"`) | `fetchAnalyticsRole` (reads the caller's own profile row by the verified token's id) and `fetchAnalytics` (the caller's own Supabase client, so RLS applies to every row) |

`runAnalytics`:
- runs the seven reads in parallel with `allSettled`, each into its own `Part<T>`;
- calls `list_team` for managers and admins only, and list quality for admins only;
- maps 42501 `scope` to `"forbidden"` and P0002 `rep` to `"invalid"`;
- never passes on the database's message.

`REACHED_OUTCOMES` now lives in `src/lib/activities.ts`: one list for Home and Analytics, re-exported from `params.ts`.

### Route: `src/app/api/analytics/route.ts`

The route handles each request in this order:
1. Checks the two-factor session with `apiSession()`: 401 when there is none.
2. Checks the per-person limit, 30 reads a minute (`analyticsRateLimited`, its own window in `src/lib/rate-limit.ts`):
   429 with `Retry-After`.
3. Parses the query strictly with Zod and resolves the range: 400.
4. Reads the role and runs `fetchAnalytics`: 403 for a refused scope, 400 for a person outside the organisation.
5. Answers 200 with `Cache-Control: private, no-store`.

Error answers are generic codes only. Nothing about the request or the database is logged.

The route is on the route inventory's reviewed list (`tests/unit/route-inventory.spec.ts`: session check, plus Zod
because it reads its query). It is also in the rate-limit spec's route list, with its own pattern test.

## Deviations from the design, with reasons

1. **Fixed instants in 2025, not 2026, for F1 and F2.**
   - A range may not end after Paris today.
   - 25 Oct 2026 and 31 Oct 2026 are still in the future on 17 Oct 2026, so the database would refuse those ranges.
   - The same edges a year earlier (31 Oct 2025, 26 Oct 2025, 30 Mar 2025) test the same rules.
   - The 2026 dates are used where nothing reaches the database: the unit tests of `resolveRange` and `parisToday`.
2. **Five more helpers.**
   - `analytics_buckets`, plus one source helper per table (activities, deals, leads, sale lines).
   - They keep team and person as separate static statements with fixed index conditions, and still read each source
     once per block (a plpgsql IF cannot split one CTE).
   - The same pattern as Home's `home_open_deals`.
3. **`jit = off` on every block and source helper.** Measured: RLS subplans push the cost estimate past
   `jit_above_cost`, and JIT doubled `analytics_sales` (see `p1-perf.md`).
4. **The suite runs right before `gate1_attack.sql`, at the end of `db-test.sh`.** It is still after `home_attack.sql`,
   as the design says. Its committed fixture adds users and an org, so placing it last means it cannot change a later
   suite's counts.
5. **Funnel stage positions are a CASE in SQL** (lead 1, qualified 2, negotiations 3), not a read of
   `pipeline_stages`. This keeps one pass. `tests/unit/analytics.spec.ts` checks the order against `openStageKeys`.
6. **Choices where the design left a detail open.**
   - `lost_reasons` leaves out `mistake`, which is reported as `lost.mistake` (it "never counts as a loss").
   - `totals.from_stock` / `direct` are revenue (money text), not sale counts.
   - Pipeline `by_person` leaves out unassigned deals ("team totals only"); the schema still allows a null id.
   - In person scope the `by_person` key is absent, not an empty list.
   - `median_minutes` is whole minutes.
7. **Batches refuses a rep with 42501 `forbidden` before the scope check**, so a rep asking for a colleague's list
   quality gets `forbidden`, not `scope`.
8. **P0002 `rep` maps to 400** (a person outside the organisation is a bad parameter). The design names 400, 401, 403
   and 429 without saying which one P0002 gets.
9. **File layout.**
   - The design says `src/lib/analytics.ts` and `analytics-server.ts`; the brief says `src/lib/analytics/*`
     (server-only).
   - The folder is used, but only `server.ts` imports `server-only`.
   - `params.ts`, `parts.ts` and `fetch.ts` are pure: no I/O and no secrets. The unit tests must import them, and the
     `server-only` package throws outside a React Server environment.
   - The page (P2) and the route are both server code anyway.
10. **No HTTP-level test of the route in P1.**
    - The 401, 400, 403 and 429 paths are proven piece by piece:
      - the route inventory (session check, Zod);
      - the rate-limit spec (the route's limiter line, plus the 30th and 31st read);
      - unit tests of the strict parse, `resolveRange` and the 403 and 400 mapping in `runAnalytics`.
    - The end-to-end API checks (`GET /api/analytics?rep=<admin>` → 403, `?foo=1` → 400, signed out → 401, mocked 429)
      are in design 5.3, which is P3.


11. **Design 3.7's "runs 6+ check that the plan stays custom" was not built as a timing-run check.** It is replaced by
    the catalog check in `analytics_attack.sql` section 0: every block function and source helper must carry
    `plan_cache_mode=force_custom_plan` (and `jit=off`) in `proconfig`. With that setting PostgreSQL never switches to a
    generic plan, so a run-6 plan check adds nothing.
12. **Sales was timed only as an admin picking `a6`.** A rep's path through `private.orders` row level security
    (created by me, or on a lead I own) is not timed. A rep-as-himself sales case is added to the P3 re-time plan
    (condition C1 below).
