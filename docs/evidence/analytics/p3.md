## What was built

### "Right now" (`src/components/analytics/right-now.tsx`)

A section of its own under "This period", set apart by a hairline and its heading "Right now · Not affected by the
dates". It follows the person filter, not the dates (a preset change leaves it untouched; e2e checks this). Four tiles
(Home's tile classes; 4 across from 1024, 2 × 2 below):

| Tile | Figure (`analytics_coverage`, P1) | Link |
|---|---|---|
| Untouched N+ days | cold, warm or negotiation leads with no entry for N days; N = 7, 30 or 90 from a small switch in the tile (`idle=` in the URL, replaceState, prefetched after a 150 ms rest like the presets) | the Leads list with exactly that filter, written by the Leads list's own `filtersToParams`: `/leads?status=cold,warm,negotiation&inactive=N[&owner=<person>]` |
| Never contacted | no entry ever (CRM or sheet) | none (no exact Leads filter) |
| No next step | warm or negotiation, no next action, no open task | none (design 1.4) |
| Overdue tasks | open tasks past due; a red status dot when above 0 | own figures (a rep, or a manager or admin who picked themselves): `/tasks?tab=overdue`; team: `/tasks?tab=overdue&scope=team`; a manager or admin who picked someone else: no link, and the sub-line says Tasks has no per-person view |

- A tile at zero reads "All caught up".
- The tile is a stretched link (the whole tile is the hit area, a chevron shows it leads somewhere). The 7/30/90 switch
  sits above the link, never inside it (no nested interactive element; axe checks this).
- The links use the person the figures belong to (the answer's own `rep`), so a link never points at another view's list.
- The page passes the signed-in person's id (`claims.sub`) to the client, so "own figures" can be linked without a
  request.

### List quality per import (`src/components/analytics/list-quality.tsx`)

- Admins only (Q11). The block renders only for an admin, the API sends `batches: null` to everyone else, and the
  database refuses them anyway (P1, 42501 `forbidden`).
- Columns: File · Imported (the Paris date) · Leads · Contacted · Reached · Deal · Won. Each share is
  "40% (2)" of the leads in the import now.
- An import whose leads are all gone reads "0 leads (all removed)", with dashes for the shares.
- The file name is the uploader's text. It is React text only, `translate="no"`, wrapped anywhere so a long name cannot
  push the table wider. It links to that import's leads (`/leads?batch=<id>[&owner=<person>]`), and that list holds the
  same count.
- A table from 768. On phones, one card per import (no sideways scroll).
- Empty: "No imports yet." with **Import leads** (`/leads/import`).
- Loading, error (Try again) and skeleton like every other card. `loading.tsx` and the Suspense fallback show the Right
  now skeleton too, with list quality for admins only (the layout's `data-role`, as for the Team card).

### Data layer

- No new SQL. Both blocks come from P1's SECURITY INVOKER functions (`analytics_coverage`, `analytics_batches`) through
  the existing `GET /api/analytics` and `src/lib/analytics/*`. So no migration and no change to
  `analytics_attack.sql`; its G4 (coverage parity with `count_leads`) and D1/D2 (batches) already cover them.
- **C4 done.** `runAnalytics` starts the six blocks every role reads at once, in parallel with the role read, and starts
  list quality and `list_team` as soon as the role is known. The route passes the pending role read. A role read that
  fails counts as a rep. A unit test checks the order. The page already read the role in parallel with its other first
  reads; it still needs the role before `list_team`, so a manager's `?rep=` can be checked against the team.
- New pure helpers in `view.ts`, all unit-tested: `coverageScope`, `untouchedHref`, `overdueHref`, `batchRows`,
  `batchHref` and `formatParisDate`. The Untouched and batch links are read back through the Leads list's own
  `parseFilters` and `rpcFilterArgs`, and must give exactly the `count_leads` arguments.

## Fixture (`tests/auth/analytics-fixture.ts`)

The fixture adds these to P2's data, all dated before the 30-day window, so every "This period" figure stays as it was:
- the last entry per hand-added lead;

  overdue);

Expected figures:
- Team, 30 days: untouched 5, never contacted 2, no next step 2, overdue 2. At 90 days: untouched 3.

fixture into its own org, next to Home's leads of the same names.

## Deviations, with reasons

1. **No new SQL, migration or attack/perf test cases for P3's blocks.** P1's functions already return every figure the
   design asks for (the "Imported" column is the batch's `created_at`). The only perf change is C1's rep sales case.
2. **"Never contacted" is a tile of its own**, as in the layout sketch, and not the Untouched tile's sub-line from the
   1.4 table. The Untouched sub-line explains the rule instead.
3. **768: Right now tiles are 2 × 2, not 3 per row.** Four tiles at 3 per row would leave one tile alone on a second
   row; from 1024 they are 4 across.
4. **`shell.spec.ts` no longer depends on spec order (fixed after the advisor's round 1).**
   - The bug: "in French, the command menu finds French words" failed when the analytics specs ran first (P2's note 9).
     Those specs move their users out of the default org. The first person in an org becomes its admin, so the shell
     user became admin, and its command menu also listed "Importer des prospects" for "prosp".
   - The fix: `shell.spec.ts`'s `beforeAll` now pins the shell user to `rep` (`setRole`), the role the test was written
     for. The change is local to the `beforeAll`. The Enter path and the `/leads` assertion are unchanged.
   - The proof: the combined run above, with the analytics specs first, passes all 21 shell tests.
5. **401 has no `Cache-Control: no-store`.** The proxy (`src/proxy.ts:126`) answers signed-out API calls before the
   route, without the header. The e2e checks the 401 status and body only; the 400, 403, 429 and 200 answers carry
   `no-store`. The proxy is outside this step. A 401 is not cached by browsers by default.
6. **Bundle not re-measured against P2.** P3 adds two small client components to the analytics route; Recharts and the
   dock prefetch are unchanged.
7. **Not run in P3:** C3 (the Supabase advisors on DEV after deploy-dev-db), because nothing has been deployed. WebKit
   was not run (Chromium only, as briefed).

## /security-review

`/security-review` was run on `git diff origin/main...analytics-ui` (head 5840cb3; application code, the migration and
the dependencies). Result: **No findings at confidence 8+**. The coordinator re-runs it on the merged diff. Summary below; the full report is not kept in the repo. What it
checked:
- **Authz.** The aal2 gate on the route (401) and the page. `private.analytics_owner`: a rep always gets their own id,
  42501 `scope` for anyone else, with no way to probe ids; a manager's or admin's id outside the org gets P0002, and the
  role is read from `profiles`, never from the request. `analytics_batches` is admin-only. The role read on the client
  only picks the extra reads. RLS backs every rule; per-person activity counts are org-readable, as accepted in Q1.
- **SQL.** Static SQL only, except the migration's constant grant loop. Every value is a typed RPC argument, and no
  PostgREST filter string is built.
- **INVOKER correctness.** All 14 functions are `security invoker`, `search_path = ''` and schema-qualified; no new
  DEFINER; grants are revoked from public and anon; no note or cost column is read.
- **Validation.** Strict Zod on the query (unknown or repeated keys give 400), and strict parsing of every answer part.
- **XSS.** No `dangerouslySetInnerHTML` or `innerHTML`. Names reach the screen only as React or SVG text. The links are
  internal paths built with `URLSearchParams` from checked uuids and integers.
- **Leaks, caching, limiter.** Fixed error codes only, and nothing logged. `no-store` on the route's answers. The
  limiter is keyed on the verified `sub`, after auth.
- **Dependencies.** recharts and react-is are pinned exactly; registry tarballs only; no install scripts.

## PR #28 CI fix: React #418 on the first render of /analytics in Chromium 156

CI run 39014870672 (head 390656d): `analytics.spec` renders_seeded_figures, `analytics-screens` "analytics en light
390", `phone.spec` phone_fit (en) and `screens.spec` "analytics en light 390" failed on Chromium (Chrome for Testing
156.0.8078.4) with React error #418 (`args[]=text`), a hydration text mismatch. The same specs passed locally on
Chromium 141.

**Cause: Intl, not time zones.** The range line under the title used `Intl.DateTimeFormat.prototype.formatRange`.
Node 22 (the server) joins the two dates with thin spaces (U+2009) around the en dash, and Chromium 156 (the browser)
uses ordinary spaces. The dev build on Chromium 156
printed the diff on `<p data-updated>`: server `Sep 18 – Oct 17, 2026` with U+2009, client the same with U+0020.
Chromium 141 still matched Node, which is why it passed locally. A probe comparing the Intl number and date calls in
`src/lib/analytics/view.ts` (money and name sorting were added to the check in the advisor round below) across Node 22 (ICU 77), Node 25/26 (ICU 78), Chromium 141 and Chrome Headless Shell
156 found two differences:
- `formatRange` differed in Chromium 156 only.
- Compact euros differed in Node 22 against every browser (`€2.0M` vs `€2M`). Only a whole-million Revenue tile shows
  this on the server, so it was a latent cause of the same error.

**Fix (`src/lib/analytics/view.ts`):**
- `formatRange` now joins two plain dates with `RANGE_DASH` (" – "), showing the year once when both dates share it:
  "Sep 17 – Oct 16, 2026", "17 sept. – 16 oct. 2026".
- `formatMoneyCompact` sets `minimumFractionDigits: 0`.
- The number and date option sets of `view.ts` now live in `INTL_NUMBER` / `INTL_DATE`. Money goes through
  `MONEY_OPTIONS` in `src/lib/money.ts`, and names are sorted with `NAME_COLLATION` (advisor round below).
- No `suppressHydrationWarning`. Paris time (explicit `timeZone`) was already right everywhere.

**Regression tests:**
- `analytics.spec` intl_server_and_browser_agree formats sample dates and numbers with the `INTL_DATE`,
  `INTL_NUMBER` and (since the advisor round) `MONEY_OPTIONS` sets, and sorts made-up accented names with
  `NAME_COLLATION`, in Node and in the browser (Paris time zone), and expects identical text and order. The compact-euro case fails without the fix.
- Unit "formatters write the same text whatever the process time zone": UTC, Paris, Los Angeles and Kiritimati via
  `process.env.TZ`.
- Unit expectations for the new range format and for whole-million compact euros.

**Reproduction:** throwaway stack (Postgres 54780, GoTrue 9980, gateway 54781), `npm run build`, `TZ=UTC next start -p
4800` (as in ci.yml). Chrome Headless Shell 156.0.8078.4 came from the Chrome for Testing archive into a scratch
